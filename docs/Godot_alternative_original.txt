마로롱 카드 전쟁 · 기존 게임 유지와 Godot 3D 표현 구성안
작성 기준: 2026-10-09
용도: 다른 채팅에서 진행 중인 Godot 기획에 전달할 개발 기준 문서

1. 목표와 현재 기준

현재 카드게임의 규칙, 카드 데이터, 덱, AI, 저장 기능을 기준으로 유지한다. Godot를 도입하는 목적은 입체적인 카드, 읽기 쉬운 손패, 전장 배치, 공격과 능력 연출을 개선하는 것이다.

현재 기준 자료는 Phase20 HTML과 이번 Phase21 UI 수정본이다. 카드 데이터는 244개 항목, 이름 235종, 진영 10개, 능력 항목 306개이다. 능력 항목 수는 구현 완료 능력 수를 의미하지 않는다. 기존에 미지원인 능력은 지원 여부를 별도로 유지한다.

이번 문서는 구성 제안이다. Godot 프로젝트, 완성된 3D 모델, 웹 내보내기, 실제 기기 성능 검증은 아직 수행하지 않았다. 다른 채팅에서 진행 중인 기획의 세부 내용은 Not available. 그 기획과 이 문서를 합칠 때 먼저 실행 플랫폼과 화면 구조를 맞춘다.

2. 이번 UI 오류를 새 구조에서 방지하는 기준

손패 호버
선택한 카드의 확대 표현만 별도로 만든다. 원래 손패의 카드 개수, 위치, 순서와 클릭 가능한 영역을 유지한다. 호버 때문에 이웃 카드가 사라지거나 한 위치로 합쳐지면 안 된다. 확대 카드의 닫힘과 손패 선택 취소는 별개로 처리한다.

능력 읽기
카드 이름과 능력 개수만 보여 주지 않는다. 능력마다 이름, 비용, 발동 시점과 조건, 효과 원문을 제공한다. 대상이 효과 원문에 포함되어 있으면 이를 보존한다. 별도 대상 데이터가 없는 카드는 임의의 대상 규칙을 만들지 않는다. 많은 능력은 확대 패널 내부에서 스크롤한다. 지원 여부와 사용 가능 여부를 구분한다.

전장 배치
각 플레이어의 전열 5칸, 후열 5칸, 시설 5칸을 실제 게임 상태의 주소와 일치시킨다. 화면에서 작은 칸으로 보이는 시설도 선택 가능한 최소 크기를 확보한다. 화면 높이 경계 하나 때문에 시설 전체를 다른 곳으로 이동시키지 않는다. 가로와 세로의 사용 가능 공간을 함께 계산한다.

정보 영역
전장 행 이름은 한국어를 가로로 읽을 수 있게 배치한다. 빈 상세 패널이 전장을 계속 좁히지 않게 한다. 카드 이름, 비용, 공격력, 방어력, 체력은 배경 연출보다 먼저 읽혀야 한다.

3. 권장 첫 단계: 기존 JavaScript 판정과 Godot 웹 표현의 결합

초기에는 현재 JavaScript가 유일한 게임 판정 주체다. Godot는 승인된 상태를 표시하고 사용자의 요청을 전달한다. 두 환경이 각자 마나, 피해, 카드 위치를 계산하는 구조는 만들지 않는다.

현재 HTML은 판정과 화면 코드가 섞여 있다. 기존 코드를 바로 삭제하거나 대규모로 다시 작성하지 말고 먼저 연결 어댑터를 추가한다. 이후 게임 판정 코드와 DOM 화면 코드를 점진적으로 분리한다.

구성 요소
GameCore: 카드와 덱, 게임 상태, 턴 처리, 합법 대상, 비용 지불, 피해, 지속 효과, AI, 승패, 저장과 불러오기.
GameAdapter: Godot 요청 검증, 기존 동작 호출, 결과 수집, 공개 상태 전달, 판정 버전 관리.
GodotPresentation: 3D 카드와 전장, 카드 선택, 마우스 호버, 배치와 공격 요청, 카메라, 효과와 음향.
WebShell: 기존 게임 코드와 Godot 웹 실행 파일의 로딩, 시작과 재시작, 연결 오류 안내.

GameCore와 GameAdapter는 JavaScript에 둔다. GodotPresentation은 GDScript로 작성하는 방안을 우선 검토한다. JavaScriptBridge를 이용해 같은 웹 페이지의 JavaScript 어댑터와 연결한다. 콜백 참조를 유지하고 연결 준비가 끝난 후 첫 상태를 전달한다.

주의: JavaScriptBridge는 웹 내보내기에 해당하는 연결 방식이다. 이 구성을 그대로 PC 네이티브 실행 파일에 가져갈 수 있다고 가정하지 않는다.

4. Godot 장면 구성 제안

BattleRoot
게임 상태를 받아 각 표현 요소에 전달하는 최상위 장면이다.

Battlefield3D
전장 바닥, 양쪽 진영, 카드 배치 지점, 합법 대상 표시, 시설 슬롯을 포함한다. 슬롯의 고유 주소는 owner, row, col로 유지한다. 3D 오브젝트 이름이나 화면 좌표를 게임 판정 주소로 사용하지 않는다.

Card3D
얇은 카드 본체, 앞면과 뒷면, 테두리, 상태 강조, 선택 영역을 포함한다. 카드 정의의 cardId와 경기 중 카드 인스턴스의 instanceId를 구분한다. 동일한 카드 여러 장을 같은 오브젝트로 취급하지 않는다.

HandView
카드 개수와 가용 너비로 손패를 배치한다. 화면 크기가 바뀌면 기준 좌표에서 다시 계산한다. 이전 프레임의 이동값에 새 이동값을 누적하지 않는다. 카드 수가 많으면 손패 전체 보기와 가로 탐색을 제공한다.

CardFocusOverlay
호버한 카드의 큰 표현과 전체 규칙을 보여 준다. 원래 손패 카드를 삭제하거나 전장으로 옮기지 않는다. 이름과 능력 설명은 화면에 정면으로 보이는 2D Control로 표시하고, 확대 카드 본체에는 작은 기울기와 재질 반사를 적용한다. 확대 패널은 손패 탐색 영역을 덮지 않는 위치를 우선 사용한다.

HudLayer
턴, 본부 체력, 현재 마나와 생산량, 턴 종료, 저장, 전투 기록을 2D 화면에 배치한다. 카메라 움직임과 독립적으로 읽을 수 있게 한다.

InputRouter
현재 화면에서 한 곳만 입력을 받도록 관리한다. 같은 클릭을 HTML과 Godot가 동시에 처리하지 않는다. 확대 패널의 스크롤, 카드 선택, 전장 드래그를 각각 구분한다.

EffectDirector
게임 판정에서 전달한 사건을 순서대로 연출한다. 공격, 피해, 회복, 보호막, 사망, 드로우, 턴 변경을 각각 처리한다. 애니메이션 완료 시점이 게임 규칙의 발동 조건이 되어서는 안 된다.

AudioDirector
카드 이동, 배치, 공격, 능력, 턴 변경의 소리를 관리한다. 반복 효과가 겹칠 때 동시 재생 수와 음량을 제한한다.

5. 카드 앞면과 아트 자산

정의 데이터
cardId, 이름, 진영, 유형, 비용, 기본 능력치, 배치 조건, 역할, 기본 공격 설명, 능력 배열을 기존 자료에서 추출한다. 능력 이름과 원문을 그대로 보존한다. 데이터 스키마 버전과 원본 해시를 기록한다.

표현 데이터
artKey, frameKey, materialKey, summonEffectKey, attackEffectKey, abilityEffectKey를 별도 파일로 둔다. 그림이나 연출을 바꾸기 위해 카드 규칙을 수정하지 않게 한다. 우선 현재 카드 ID에 대응하는 표를 만든다.

카드 그림
현재 공용 역할 아이콘은 임시 표시다. 개별 카드 일러스트가 준비되기 전에는 역할, 진영 색, 실루엣과 이름을 조합해 구분한다. 완성된 카드 그림이 있다고 문서나 화면에서 표시하지 않는다. 아트 목록, 규격, 제작 주체와 사용 권한은 별도로 결정한다.

앞면 텍스처
SubViewport와 ViewportTexture를 이용해 카드 앞면 UI를 3D 카드 표면에 표시하는 방안을 사용할 수 있다. 카드마다 매 프레임 앞면을 다시 그리지 말고 데이터가 바뀔 때 갱신하는 방식부터 측정한다. 정적인 일러스트와 테두리는 공유 자산으로 사용한다. 최종 텍스처 해상도는 실제 화면의 글자 크기와 메모리 측정 후 정한다.

전체 능력 설명은 3D 카드의 작은 표면에 모두 넣는 것으로 끝내지 않는다. 정면 2D 확대 패널을 함께 사용해야 한다.

6. 입력과 상태 전달 규약 제안

Godot에서 JavaScript로 보내는 요청
schemaVersion, matchId, commandId, expectedStateVersion, actorInstanceId, actionType, targetAddresses를 포함한다.

actionType은 카드 선택, 배치 요청, 공격 요청, 이동 요청, 능력 사용 요청, 턴 종료 요청처럼 구분한다. 선택과 호버는 화면 상태이며 마나를 지불하지 않는다. 카드 사용과 공격은 실제 판정 요청이다.

어댑터 검증
경기 식별자, 상태 버전, 현재 플레이어, 인스턴스 존재, 사용 가능 조건, 비용, 합법 대상, 중복 요청을 확인한다. 기존 코드의 최종 실행 경로를 호출해 비용이 한 번만 지불되게 한다. 처음 연결할 때 모든 게임 함수를 공개 API로 내보내지 않는다.

JavaScript에서 Godot로 보내는 결과
commandId, accepted, reason, stateVersion, presentationSnapshot, events를 포함한다. 요청이 거절되면 카드와 손패를 기존 상태로 돌리고 이유를 표시한다. 승인된 요청만 확정 배치나 피해 연출로 이어진다.

표현용 상태
내 공개 정보, 내가 볼 수 있는 손패, 상대의 공개 전장, 상대 손패 수, 상대 카드 뒷면만 제공한다. 상대 덱 순서와 비공개 카드 이름을 표현용 상태에 넣지 않는다. 로컬에서 양쪽 상태를 보유하는 기존 게임의 특성은 유지하되, 새 화면 계층에 불필요한 비공개 정보를 넘기지 않는다.

사건 자료
공격자와 대상 주소, 확정 피해, 반격, 보호막 변화, 회복량, 사망, 이동, 최종 위치를 판정 결과에서 전달한다. Godot가 공격력에서 방어력을 다시 빼거나 주사위를 다시 굴리지 않는다. 확정 결과가 도착하기 전 표시하는 예상 피해는 기존 공개 정보 기반의 미리보기로 명확히 구분한다.

현재 전투 기록이 모든 사건을 구조화해 제공한다고 가정하지 않는다. 어댑터 구현 단계에서 기존 실행 함수에 사건 수집 지점을 추가하고 순서를 검증해야 한다.

7. 연출 흐름

호버: 포인터가 카드에 잠시 머무르면 확대 표현을 만든다. 다른 카드로 이동하면 확대 대상만 바뀐다. 원래 손패는 유지한다.
선택: 선택 강조와 합법 대상만 나타낸다. 취소하면 원래 상태로 돌아간다.
배치: 드래그 중에는 임시 카드만 포인터를 따라간다. 놓은 위치가 합법이고 사용이 승인되면 손패 감소와 확정 배치를 반영한 뒤 배치 효과를 재생한다.
공격: 대상 선택 중에는 방향선과 예상 피해를 보여 준다. 승인 후 카드 전진, 타격, 확정 피해, 반격과 사망을 판정 순서에 맞게 재생한다.
능력: 능력별 대상과 비용을 먼저 읽을 수 있게 한다. 확정 후 투사체, 회복, 보호막이나 지형 효과를 재생한다.
취소와 재시작: 진행 중인 임시 표현과 효과 대기를 정리한다. 이전 경기의 지연 콜백이 새 경기의 카드나 체력을 바꾸지 않게 한다.

카드 간 물리 충돌이나 카메라 화면 밖으로 나간 여부로 전투 결과를 결정하지 않는다. 연출 속도를 높이거나 건너뛰어도 최종 상태가 같아야 한다.

8. 카메라와 전장 스타일

첫 시제품은 전장을 읽기 쉬운 고정 카메라로 만들고 약한 입체감만 적용한다. 정사영 또는 낮은 원근 카메라를 비교한 후 선택한다. 가까운 내 카드와 먼 상대 카드의 글자 크기가 지나치게 달라지지 않게 한다.

실제 전장 위 카드에는 이름, 비용, 전투 능력치와 상태를 남긴다. 자세한 규칙은 확대 패널에서 읽는다. 바닥, 조명과 입자 효과가 슬롯 경계나 대상 강조 색을 지우지 않게 한다.

일반 공격, 큰 능력, 영웅 등장에 각각 다른 연출 강도를 준다. 매 공격마다 전체 화면을 흔들거나 카메라를 크게 움직이지 않는다. 화면 흔들림과 번쩍임을 줄이는 설정, 연출 속도 설정을 둔다.

9. 실행 플랫폼 결정

현재 게임을 빠르게 유지하면서 연결하는 첫 시제품은 Godot 웹 내보내기와 기존 JavaScript 결합이 적합하다는 제안이다. 웹에서는 Compatibility 렌더러와 WebGL 2.0을 기준으로 설계한다. 데스크톱 Forward+에서 가능한 효과를 웹에서도 그대로 쓸 수 있다고 가정하지 않는다.

공식 문서 확인 기준으로 Godot 4의 C# 프로젝트는 웹 내보내기가 지원되지 않는다. 초기 웹 표현 코드는 GDScript로 구성하는 방안을 권장한다. 단일 스레드 웹 내보내기로 시작하고, 추가 스레드가 필요해지면 배포 헤더와 환경 요건을 검토한다.

Godot 웹 결과물은 현재 독립 HTML 한 파일과 다르게 실행 파일과 데이터 파일을 함께 배포해야 한다. 첫 시제품은 로컬 웹 서버에서 검증하고 이후 정적 호스팅 구조를 결정한다.

네이티브 PC 버전을 최종 목표로 정하면 별도 단계가 필요하다. 기존 규칙을 GDScript 등으로 이식하고 JavaScript 버전과 같은 입력에서 같은 결과가 나오는지 비교하는 방식이 후보이다. 브라우저와 네이티브에서 판정 코드를 영구적으로 각각 수정하는 상태는 피한다. 이식 완료 후 판정의 기준 구현을 하나로 정한다.

10. 구현 순서와 완료 기준

단계 A · 기존 UI 안정화
이번 Phase21을 기준으로 손패 호버, 실제 능력 표시, 시설 높이, 행 이름, 빈 상세 패널 문제를 확인한다. 같은 카드 규칙과 AI를 유지한다.

단계 B · 연결 없는 Godot 표현 시제품
대표 카드와 전열, 후열, 시설을 만든다. 6장과 12장 손패, 호버, 선택, 전체 규칙 읽기를 먼저 검증한다. 이 단계에서는 가짜 전투 수치를 실제 게임으로 오해하게 표시하지 않는다.

단계 C · JavaScript 어댑터 연결
시작 상태, 카드 선택, 배치, 턴 종료를 연결한다. 중복 요청, 잘못된 대상, 상태 버전 불일치, 재시작을 검증한다. 현재 저장 자료를 불러온 뒤 같은 공개 상태가 표시되어야 한다.

단계 D · 전투와 능력
일반 공격, 반격, 보호막, 회복, 사망부터 연결한다. 대표 직접 사용 능력, 지속 효과, 함정과 복합 효과 순으로 추가한다. 능력 설명을 보여 주는 것과 해당 능력을 실제로 사용할 수 있는 것을 따로 검증한다.

단계 E · 진영별 연출과 아트
각 진영의 카드 테두리와 재질, 일러스트, 배치와 공격 효과를 연결한다. 같은 판정 사건에 다른 표현만 적용한다. 시각 효과 추가 후에도 호버와 대상 선택 검사를 다시 수행한다.

단계 F · 성능과 배포
성능 목표는 검증 전 제안으로 데스크톱 60fps, 저사양 환경 30fps를 둔다. 실제 기기 사양과 브라우저를 기록한 후 목표를 확정한다. 최대 손패, 모든 전장 슬롯, 여러 효과와 긴 능력 설명을 함께 켠 상황을 측정한다.

11. 필수 검증 목록

손패 1장, 6장, 12장 이상에서 각 카드로 포인터를 이동할 수 있다.
호버 전후 손패의 인스턴스, 개수, 순서가 같다.
원래 카드의 선택 영역이 확대 오브젝트에 의해 막히지 않는다.
모든 등록 능력의 원문을 읽을 수 있고 비용과 조건이 빠지지 않는다.
시설 10칸과 전장 20칸의 게임 주소와 화면 주소가 맞는다.
1920×1080, 1920×999, 1366×768, 2560×1440에서 각 영역을 확인한다.
모바일을 지원 대상으로 결정하면 별도 손패 탐색과 터치 선택을 검증한다.
잘못된 드롭, 취소, 더블 클릭에서 비용이 중복 차감되지 않는다.
예상 피해와 실제 판정 결과를 기존 게임과 비교한다.
연출을 생략하거나 빨리 재생해도 경기 결과가 같다.
저장과 불러오기, 재시작, AI 진행과 관전에서 이전 경기 효과가 남지 않는다.
상대 비공개 카드와 덱 순서를 확대 패널에서 볼 수 없다.

12. 다른 채팅에 전달할 작업 지시

마로롱 카드 전쟁의 Phase20 게임 규칙과 AI를 유지하고 Phase21 UI 수정본을 참고해 Godot 3D 표현을 설계해 주세요. 초기 목표는 기존 JavaScript 판정과 Godot 웹 표현을 연결하는 것입니다. 먼저 6장과 12장 손패, 호버 확대, 전체 능력 설명, 전열·후열·시설 슬롯의 입력 가능한 시제품부터 만들고, 게임 판정은 별도 어댑터를 통해 연결해 주세요. 손패 호버 때 나머지 카드 위치와 순서가 유지되어야 합니다. 능력의 비용·발동 조건·효과 원문을 모두 읽을 수 있어야 합니다. 승인되지 않은 요청이나 애니메이션 자체가 마나·피해·카드 위치를 바꾸면 안 됩니다. 네이티브 PC 실행을 우선한다면 JavaScriptBridge 연결안과 구분해 규칙 이식 및 동일 결과 검증 계획을 먼저 제시해 주세요.

13. 공식 문서 확인 자료

Godot 웹 내보내기
https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html
확인 용도: WebGL 2.0, Compatibility 렌더러, C# 웹 제한, 단일 스레드 웹 내보내기.

JavaScriptBridge
https://docs.godotengine.org/en/stable/tutorials/platform/web/javascript_bridge.html
확인 용도: 웹에서 JavaScript와 Godot 연결, 콜백 생성과 참조 유지.

SubViewport 텍스처
https://docs.godotengine.org/en/stable/tutorials/shaders/using_viewport_as_texture.html
확인 용도: 별도 화면을 텍스처로 만들어 3D 표면에 적용하는 구성.

문서의 구체적인 코드 구조, 연출 방식, 성능 목표와 개발 순서는 프로젝트를 위한 제안이다. 공식 문서가 마로롱 프로젝트의 성능이나 개발 완료를 보증하는 것은 아니다.
